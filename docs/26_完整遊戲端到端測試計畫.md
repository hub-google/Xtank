# X-TANK｜Windows EXE 全遊戲端到端測試計畫（QA Test Plan）

> **測試帳號已建立**：請先閱讀 [27｜3 組可登入的測試帳號與密碼安全查詢方式](27_測試帳號與跨對話接續.md)。每次 QA 從連接的 Supabase `xtank.qa_credentials` 取得當次密碼，不得把憑證提交到公開 repository。
> 版本：QA-PLAN 1.0｜2026-10-27｜來源：[`24_完整遊戲PRD.md`](24_完整遊戲PRD.md)、[`25_Supabase完整資料庫架構.md`](25_Supabase完整資料庫架構.md)  
> **用途**：之後可以直接要求 AI「依照本文件完整測試 X-TANK」，按順序實際執行、蒐集證據、修 Bug、回歸，不准用程式能 build 冒充遊戲能玩。

## 0. 不可違反的測試原則
1. **必須啟動 GitHub Actions 打包出來的 Windows Portable EXE 本體**，不是把 Vite 頁面放進瀏覽器就冒充 EXE。
2. 優先使用獨立雲端 Windows 電腦（GitHub Actions `windows-latest`；不得操作使用者個人電腦）。如果未取得雲端 Windows 真正執行證據，該情境列 BLOCKED。
3. 測試使用者動作是真正按按鈕/鍵盤/滑鼠；不得直接修改記憶體中的 HP、勝負、時間、移動座標來製造 PASS。可使用**唯讀** `window.xtankDiagnostics()` 觀察。
4. 自動化可用 Playwright 透過 Electron 開啟的 Chrome DevTools port 進行點選/錄 trace，但不能代替原生 EXE 啟動；每次記錄 EXE SHA256、Windows build、GPU/軟體渲染、commit SHA、run ID。
5. 要截圖、stderr/log、網路封包摘要、時間和 DB 查詢作為證據；沒有執行的案例絕不能標 PASS。
6. 狀態只能是 **PASS（實測符合）/ FAIL（實測不符）/ BLOCKED（環境限制、無法執行）/ NOT_IMPLEMENTED（需求尚無程式）/ NOT_RUN（本輪未測）**。
7. 執行完必須寫：測試案例逐筆 verdict、失敗重現步驟、預期與實際、GitHub issue/修復 commit、回歸證據、新的 EXE 下載連結。
8. 單機與 LAN 原型可測現有功能；Auth/商店/官方 WSS/永久戰績/社交功能若仍未串接，列 NOT_IMPLEMENTED 而不是 PASS。

## 1. 測試設備、前置條件和資料
- 專案：https://github.com/hub-google/Xtank
- Windows EXE workflow：https://github.com/hub-google/Xtank/actions/workflows/windows-exe.yml
- 現有 GUI 測試程式：`scripts/windows-gui-qa.cjs`；GUI 規則：`docs/23_Windows_EXE_GUI_QA.md`。
- 測試階段分層：L0 原生啟動；L1 單機完整對戰；L2 雙原生 EXE 同 LAN；L3 跨不同網路的公開 WSS；L4 Supabase 帳號與商店經濟；L5 社交/活動/運營；L6 回歸、效能、破壞性測試。
- Supabase：使用 **隔離測試 Auth 玩家** A/B/C，避免更動真實玩家資料；DB schema `xtank` 已部署，測前 snapshot 及測後刪除測試資料需可審核。
- 測試人員/自動化 runner 不得把 Supabase secret/service_role 當成客戶端設定寫入日誌、截圖或 artifact。
- 測試 fixture：8 種坦克 X/D/M/R/H/A/O/S、3 模式 FFA/TDM/FLAG_HOLD、3 地圖 desk/chess/circuit、7 武器、6 道具、兩玩家+最多 8 席、限制與被封鎖玩家。
- 網路條件：好網 0–50ms、一般 150ms、差網 250ms+2% loss、WebSocket 斷線 10/29/35s；這些需控制注入並記下真實量測，不准猜測。
- 參照每個 Run 的 `XTANK-Windows-GUI-Evidence`（`REPORT.md`、`results.json`、`trace-*.zip`、screens、logs）判定是否真的通過。
- **測試工作流程可以失敗**：此時 artifact 和報告比 Actions 的單一紅/綠標記更重要；逐項判讀每個情境。

## 2. 唯一主流程：按畫面走完，不准跳步
```text
啟動 EXE
 ├─ 若離線/載入失敗 → 提示、重試/安全關閉
 └─ 首畫面 → 訪客進入 / 註冊 / 登入
              → 玩家資料/設定載入
              → 主大廳
                 ├─ 機庫: 8車展示 → 選車 → 五屬性/技能
                 ├─ 背包: 武器/道具 → 7+7 配裝 → 儲存
                 ├─ 商店: 商品/價格 → 購買 → 錢包扣款 → 背包增加
                 ├─ 社交: 好友/公會/信件/排行
                 └─ 進入戰鬥:
                      ├─ 單機練習（AI）
                      └─ 官方多人房間/配對 → 兩真人進房
                           → 模式/地圖/隊伍/裝備 → 全員 READY → 房主開局
                      → 戰場倒數 → 開火/移動/道具/技能/碰撞/持旗
                      → 死亡重生 → 勝負自然達成
                      → 結算 K/D/A/傷害/名次/XP/金幣
                      → Supabase 正式獎勵唯一入帳
                      → 返回大廳 → 等級/錢包/背包/戰績一致
                      → 再戰一局 → 登出關閉 EXE
                      → 重新啟動登入 → 永久資料一致
```

## 4. 測試順序、停止規則與交付門檻
1. **Gate 0**：`npm test`、`npm run build`、EXE 打包成功。它只是進場資格，不是驗收 PASS。
2. **Gate 1**：A01–A12 全部可執行案例 PASS；A02/A08 未通過禁止宣稱可玩 EXE。
3. **Gate 2**：72 組 E01、核心 E02–E22、自然結算 F01–F05/F11/F12 過關，才可標「單機可玩」。
4. **Gate 3**：D01–D15、E19–E20、F08/F11 實際雙原生 EXE 過關，才可標「LAN 多人可玩」。
5. **Gate 4**：B、C、D16、F06–F10、H02–H04 全過，才可標「正式線上帳號與永久經濟可玩」。
6. **Gate 5**：G、H，真正 Windows 不同網路人類試玩（至少兩玩家完整三局），才可標「完整遊戲 Alpha 驗收」。
7. **未實作也要建 testcase**；不得把未實作從分母移除宣稱 100%。
8. **一項阻斷**：EXE 無法啟動、不能登入、開始按鈕無反應、多人不能進房、作弊可改正式幣、跨局資料遺失，即整體標 **FAIL/BLOCKED**，不因其他項 PASS 而強制綠燈。
9. 修改程式後從受影響案例回歸開始，最後再執行所有流程；若修 A 導致 B 又壞，不能算修復完成。

## 5. 自動化建議與現有實際涵蓋
- 先使用 `scripts/windows-gui-qa.cjs` 透過 `windows-latest` 開真 EXE，現有程式涵蓋 72 個 Tank/Mode/Map、WASD、7 武器、道具、碰撞、死亡重生、自然結算、LAN、重連與同步。
- 現有 GUI harness 不代表所有案例已 PASS：逐個查看 Run 的 `results.json` 與 `REPORT.md`，出現 BLOCKED 就不能報綠燈。
- 待開發 Auth/DB API 後，增加隔離帳號自動測試；不得從 Windows GUI harness 直接使用 service_role 來冒充玩家結算。
- 針對 SQL 使用 transaction + rollback 的整合測試；私有密鑰只在可信 runner secrets，日志絕不可輸出。
- 完整 GUI 截圖加 Playwright trace，而非只把 API response=200 當成功；原生 Windows 遊戲渲染需要畫面與邏輯雙證據。
- 測試程序應使用專用測試帳號、測試房間與測試資料前綴，並對任何寫入原本 Game 公共資料表的行為視為 FAIL。
