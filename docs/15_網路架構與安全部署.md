# 15｜真正多人連線：同步、作弊防護與免費部署評估 v0.1

## 1. 對戰一定需要權威伺服器
GitHub Pages **只能託管靜態前端**，不能在 Pages 內執行持續運作的多人遊戲伺服器。前端用 TypeScript + Three.js + Vite，伺服器採 TypeScript 的 Room/Match 狀態機；同一份 shared 協定與遊戲常數可在兩端引用。

流程：Browser A/B/C… ↔ WSS Gateway ↔ Authoritative Room Server ↔ 持久化帳號/戰績服務。
P0 優先「1 個房間程序可控地跑 2–8 人」，不得用彼此瀏覽器直接決定擊中判定。

## 2. 房間伺服器真相
- 專屬時基，固定更新 tick 20Hz（P0 起始），每個 Client 每秒輸入 10–20 次、快照輸出 10Hz；依負載與畫面狀態動態調整。
- 客戶端僅送 input：移動意圖、瞄準、射擊按鍵、武器槽、道具指令與序號。**不得送目前 HP、已造成傷害、被打死、獲勝分數或最終位置作為可信事實**。
- 伺服器依 tick 執行：輸入驗證 → 移動與碰撞 → 投射物 → 命中傷害 → 道具／旗幟 → 計分 → 廣播快照。
- 客戶端做本地玩家預測 + 帶 sequence ack 的回滾修正；遠端玩家用 100–150ms 插值緩衝，避免抖動；直射武器可做不超過 200ms 的回溯命中補償（P）。
- 坐標與朝向採浮點傳送但每 tick 限速、限轉、限射速；避免浮點漂移積累；通訊採 schema 驗證和 server authoritative UUID。

## 3. 安全與穩定性
- token 只表示身份，不給客戶端提升角色與商店資產的能力；每 socket 繫結 playerId。
- TLS/WSS、Origin 白名單、加入速率限制、密碼房以伺服器雜湊驗證、記錄 rate-limited 異常事件。
- 同一 playerId 同時最多一條 LIVE 連線；重連發新 session epoch，舊連線的遲到封包全部丟棄。
- 輸入包拒絕過大的時間跳躍、重放 sequence、跨房行動、未擁有武器、冷卻內連發與非合法位置。
- 心跳 5s，15s 無訊息標示斷線；保留房內位置 30s 可重連；超時依房間規則讓 AI 接管或退出。
- 每局生成 matchId + seed + 規則版本，保存摘要事件供追查；敏感資訊不得送日志。
- WebSocket 無連線時，使用者看得到明確服務不可用／容量限制，不顯示虛假的「連線成功」。

## 4. 零付費部署的真實限制
可選架構：
- A：GitHub Pages（前端）+ Cloudflare Workers / Durable Objects（伺服器房間）+ SQLite/D1（適用時）。適合小規模、容易配置；**實時每秒訊息會迅速耗盡免費請求數，不能預設完全免費 24h 多房運行**。
- B：GitHub Pages（前端）+ 自己可長駐的免費或自有主機（Node.js + ws）+ SQLite/Postgres。若確定機器可長時開機與對外 WSS，訊息不計入 CF DO 請求；但需要維運、SSL、防火牆，並非天然零成本。
- C：付費持久遊戲節點。公開長期服務且有活躍玩家時再選。

**2026-10 CF 官方價格頁**：Workers Free 可使用 SQLite backed DO；DO 免費 100,000 requests/day、13,000 GB-s/day；超額免費操作會失敗。假設 8 玩家每秒各送 10 個 WebSocket 輸入包，就有 80 messages/s，單單進站就約 1,250s（20.8 分鐘）消耗 100,000 request 額度，尚不含快照、連線及其他請求。因此 CF Free **只能先做短時程驗證，不能承諾 8 人常時營運**。官方資料：https://developers.cloudflare.com/durable-objects/platform/pricing/ 、 https://developers.cloudflare.com/durable-objects/best-practices/websockets/ 。

Durable Objects Hibernation WebSocket API 可降低閒置費用，但 LIVE 房間持續 tick 與計時器時一般無法休眠；不同於聊天室，不可指望長局內 hibernation。需要實測費用與處理時延。

## 5. 服務選擇
P0 首先把權威房間模組設計成和平台無關：純 TS 模擬核心 + 可換的網路適配器。先在 GitHub Actions 建立本機雙客戶端集成測試，再選擇能真正常駐的測試節點。伺服器獨立版本與 Github Pages URL，不把 WSS 祕鑰塞進 GitHub Pages 前端。

## 6. 量化目標（不是目前已達成）
- 8 人同場平均快照往返延遲適應 150ms RTT；250ms RTT 仍能操作且沒有可穩定重現的穿牆／雙重擊殺。
- 維持 30 分鐘穩定局至少 95% 輸入可被按預期 ack；斷線重連成功率 99%（受測環境內）。
- 對 10,000 次惡意封包注入沒有未授權改分、重複經濟結算、非預期伺服器崩潰。
- P0 伺服器模式至少支援 1 房 8 人；P1 依監控擴容和排隊。

注意：本檔只是架構規格，**目前尚未部署多人伺服器**。
